kime 与 Laya 的 P0 基线实测

  • 阶段： P0
  • 问题： 把 kime 和 Laya 在只有 CPU 的机器上完整跑一遍，看看 Laya 的缺陷、kime 的实现和规格之间有什么差距，以及后面阶段能直接用的基线数字。
  • 结论：
    • 整条链路在只有 CPU 的 Intel Mac 上就能跑通，成本是约 6 分钟编译加 644 MB 权重。
    • Laya 有三个缺陷，都能亲眼看到：选项排列会改变答案，答案依赖标签字面，act_probability 不可用。
    • 同一 state 上的问题数从 1 增加到 10，耗时变成 7.3 倍，说明 state 没有复用。
    • kime 0.1.8 的指标定义可以直接对拍。
    • kime.policy 字段会被静默忽略，响应里也没有缓存字段。

Laya 的三个缺陷

1. 选项排列会改变答案。 下面四组改动只针对 team 这道题：

改动team 的概率urgencychurn
原始billing 1.0，其他 0.01.8710.0117
选项顺序反转billing 0.998，other 0.001，sales 0.0011.8710.0117
加入错误选项 legalbilling 1.0，legal 0.01.8710.0117
标签改成 option 1..4，描述不变option 1 0.793，其余 0.147、0.04、0.021.8710.0117
  • 反转选项顺序后，team 的概率变了，另外两题一点没变。这说明每个问题单独前向，但同一个问题内部，选项的排列会影响 logits。
  • 加一个明显错误的选项，team 几乎不动，因为 billing 已经饱和在 1.0。要观察候选集效应，必须先构造一个不饱和的问题。

2. 答案依赖标签字面。 描述不变，只把标签换成中性 id，team 就从 1.0 塌到 0.793。kime 增强表中「rename choice labels to neutral ids, 20%」这一项要修的就是它。

3. act_probability 不可用。 三道题的 act_probability 全是 1.0，包括最大概率只有 0.3686 的 urgency：

team    | choice | confidence 0.9999 | act_probability 1.0
urgency | score  | confidence 0.1243 | act_probability 1.0
churn   | noul   | confidence 0.9883 | act_probability 1.0

这和 kime spec/02-prior-art.md 的记录一致：act head 从没训练过（0.0 * act.sum()），AUROC 0.30。所以 Laya 只能在 NLL、ECE、Brier 上当基线。

另外，同一个 urgency，响应里的 confidence 是 0.1243，answer_confidence 是 0.3686。前者是熵公式 1 − H(p)/ln k，后者是 max(p)。报告里两者都叫「置信度」，做校准时要分清取的是哪一个。

耗时随问题数和选项数增长

同一个 state，同样的 choice 问题，三次运行取中位数：

问题数124810
耗时136 ms266 ms428 ms888 ms993 ms
相对 1 个问题1.0x2.0x3.1x6.5x7.3x
选项数2481632
耗时125 ms165 ms228 ms415 ms610 ms
  • 问题数增加时，耗时近似线性增长，state 没有复用。P8 的完成标准就拿这条曲线作对照。
  • 选项从 2 个增加到 32 个，是 16 倍选项、4.9 倍耗时。Laya 的 compat 布局把所有选项放进同一个序列，选项多了只是序列变长，前向次数不变。

指标对拍

kime eval 接受任意符合格式的 JSONL。手写 7 行，789 ms 就能出完整报告。rows.tsv 每行给出 gold、pred、confidence、correct 和逐选项的 probs；加上 --answers 可以不加载模型重新评分。用 rows.tsv 手算的结果和报告一致：

手算       ECE=0.357176  Brier=0.573607  NLL=1.044533
kime 报告  ECE=0.3572    Brier=0.5736    NLL=1.0445

同一份数据，T = 1.0 时 ECE 是 0.3572，T = 3.0 时是 0.1452。只有 7 条数据，这只能说明流程通，不能当结论。

kime 0.1.8 和规格的差距

  • 响应里没有 cache 字段。 spec/03-api.md 的示例里有 "cache": {"state": "hit", "answers": "miss"}，但它属于扩展块，只在原生模型的响应里出现；Laya compat 路径不给这个字段。所以 P8 在 Laya 这一侧没有现成的对照可读，要自己测。
  • kime.policy 被静默忽略。 按 spec/04-semantics.md，传入 {"wrong": -3, "correct": 1, "abstain": -0.5} 后，响应应该带 decision，阈值是 0.625。实测响应的顶层字段只有 model、answers、usage，也没有报错。源码中 policy 只出现在 kime-train 里。P6 的代价矩阵阈值要自己实现。

Qwen3 零样本

指令版 Qwen/Qwen3-0.6B，使用聊天模板，只在候选集内归一化：

标签概率
sales0.4882（argmax）
billing0.4471
technical0.0625
other0.0021

正确答案是 billing，客户被重复扣费并威胁取消。0.6B 零样本选错了，而 Laya 给 billing 1.0。

读标签 token 的零样本读法本身成立，但有四个陷阱：

  1. 标签放进 prompt，模型会去抄标签。 prompt 里只能给描述，标签作为候选出现在作答的位置。
  2. 候选的首 token 必须互不相同。 option 1..4 的分词是 [2047, 220, 16/17/...]，首 token 都是 option，归一化后必然全是 0.25。这不是模型认为四个一样，而是读法失效了，要改成累加多个 token 的序列打分。
  3. 对空格和大小写敏感。 billing、 billing、Billing、 Billing 是四个不同的 token，概率能差两三个数量级（实测 billing 1.6e-8， billing 6.1e-7）。
  4. 作答前缀要和模型实际的输出格式一致。 选项写成 - 标签: 描述 的列表时，模型常常先照抄 - 。直接在作答位置读标签，几个标签的概率都很低，单 token 的标签（如 other）少乘几个概率，就占了便宜。见 欧冠反事实对照：不加前缀时 7 个请求里有 2 个和贪心生成不一致，都误选了 other。本节的数字是首 token 读法、不加前缀得到的，也可能受这一条影响。

这四个陷阱说明，读标签 token 的做法泛化不到任意标签集。DUAN 用学出来的结尾标记加决策头，原因就在这里（design.md 第 3、5 节）。

Intel Mac 的 Python 环境

PyTorch 从 2.5 起不再发布 macOS x86_64 的 wheel，能用的最高版本是 2.2.2，它要求 Python ≤ 3.12、numpy < 2，transformers 也要停在 4.57 以下。安装命令见 tools/ref/README.md。

分析

  • 选项排列会改变答案、act_probability 不可用，这两条分别由 DUAN 的分段布局（design.md 第 3.4 节）和 P6 的置信度头来解决。答案依赖标签字面，由中性标签增强来解决。
  • P1 不依赖任何模型权重。指标定义已经和 kime 对上，duan-calib 的对拍测试直接调用 kime-eval。
  • 没有跑 kime 的 tools/eval/build_suites.py 和 run_laya.py，它们要下载约 3 GB 数据集，还要另装 laya 包。这两个脚本等 P4 要和 kime 的公开数字逐行对比时再跑。

尚未验证：

  • .kime 打包格式，以及非 Laya 后端的 --precision int8 路径；
  • kime-train 在全量数据上的真实速度。本次只跑了 78 行、10 步，每秒 57 个 token，不能外推。
