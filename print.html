DUAN

介绍

一个不生成文本的决策模型。

给它一段 state（一封邮件、一张工单、一份 JSON）和一组问题，它直接输出一组校准过的概率，而不是写一段回答。问题有三种：多选一、有序打分、判断真假。

主干用 Qwen3-0.6B，用 Burn 从零实现，重点场景是中文。

这个站是这个项目的公开笔记：设计怎么定的、机制为什么是这样、实测看到了什么。源码仓库目前是私有的。

为什么不做生成

要回答「这封工单该转给哪个团队」，最直接的做法是让大模型写一段话，再从里面抠出答案。这个做法有三个问题：

  • 慢。 生成 50 个 token 和做一次前向，差一个数量级。
  • 贵。 每多一个 token 就多一次计算，而答案其实只有一个词。
  • 概率不可信。 生成模型说「billing，置信度 95%」时，那个 95% 是编出来的，不是校准过的。

一个 state 上往往要同时问好几个问题：该转给谁、多紧急、客户会不会流失。如果每个都生成一段话，代价翻好几倍。

所以这个项目反过来做：把所有问题的所有选项放进一次前向，直接读每个选项的分数。 不生成任何一个 token。

三种题型

题型要回答什么输出
choice（多选一）该转给哪个团队每个选项一个概率，和为 1
score（有序打分）有多紧急（1 到 5）每个档位一个概率，外加期望分
noul（判断真假）客户会不会流失一个概率

三种题型共用同一个主干、同一次前向。区分它们的是序列里的一个类型标记和结尾的一个特殊标记。

从哪读起

想搞懂这个模型为什么长这样，读编码器与解码器做决策的差别。这是全书的核心：从一个真实的客服工单讲起，一路推到「为什么标记要放在选项后面」「为什么位置要重算」「为什么这样能得到零翻转率」。不需要预备知识，懂基本的注意力就够了。

想知道一次请求内部发生了什么，读一次请求的数据流。

要查具体参数，读设计规格。它是参考资料，不必顺序读。

想看数据，读Laya 的缺陷实测——三个已知缺陷都被量了出来；以及反事实对照。

只想知道词是什么意思，术语表一页够了。

三句话概括设计

  • 主干是 Qwen/Qwen3-0.6B-Base。 对照组是用同一批数据、同一个损失微调的 laya-multilingual。
  • 一次前向回答一个 state 上的所有问题。 选项段之间互不可见、位置重计，所以交换两个选项只会交换两个 logit，state 的 KV 还能缓存复用。
  • 概率要校准。 指标、损失和校准契约都有明确的定义，报告里的数字可以直接和其他实现比较。

关于这些数字

这个项目的几乎所有数字都标了出处和测量条件。没标条件的数字不要引用——它们可能是设计目标，不是实测值。

如果发现哪里对不上，那就是文档的问题，不是来源的问题。这个站的目标是每个数字都能追到一行原始记录。

编码器与解码器做决策的差别

要给选项打分，只有一件事真正决定了模型得长什么样：读分数的那个位置，看得见什么。

这句话听着抽象。走一遍就清楚了，我们拿一个例子从头走到尾。

1. 一个例子

一封客户工单：

上个月我的信用卡被扣了两次款，请立即退款。

模型要回答：该转给哪个团队。三个选项：

选项文本
billing账单与退款
sales售前咨询与报价
legal合同与合规

工单正文是 state，问题是「该转给哪个团队」。模型输出的不是一段话，是三个分数。记住这封工单，下面每一步都用它。

2. 一个位置里装了什么

打分是拿某个位置的隐藏状态过一个小网络，得到一个数。所以先得问：那个位置的隐藏状态，里面装的是啥？

装的是「它能看见的那些 token」压缩出来的东西。能看见谁，由注意力决定。有两种：

  • 因果注意力（Qwen3 这类解码器）：第 i 个位置只能看见 0 到 i，也就是它自己和自己之前。
  • 双向注意力（ModernBERT 这类编码器）：每个位置看得见整段。

画出来，s 是工单正文，q 是问题，o₁ 是 billing，m 是我们准备读分数的标记：

     因果                       双向
        s q o₁ m                  s q o₁ m
    s   ■ · ·  ·              s   ■ ■ ■ ■
    q   ■ ■ ·  ·              q   ■ ■ ■ ■
   o₁   ■ ■ ■  ·             o₁   ■ ■ ■ ■
    m   ■ ■ ■  ■              m   ■ ■ ■ ■

左边每一行是个「到目前为止」的压缩，右边每一行是整段的一个摘要。

这个差别看着小，它是后面所有事情的地基。

3. 标记为什么要放在选项后面

先看右边。m 在末尾，能看见 o₁；o₁ 也能看见 m。谁放哪都行。

再看左边。m 能看见 o₁，因为它排在 o₁ 后面。把 m 挪到前面去：

        s q m o₁
    m   ■ ■ ■ ·     ← m 这一行看不见 o₁

m 的隐藏状态里根本没有 o₁ 的信息。拿它给 o₁ 打分，等于蒙着眼打分。

所以标记必须放在选项文本后面。 这不是排版偏好，是「读分数的位置得看得见它要打分的那个选项」的直接结果。

在编码器里这从来不是问题——它总是看得见全文。所以不少人从编码器换到解码器时，会照着原来的习惯把标记放前面，然后发现模型在瞎猜。原因就在这里。

4. 选项多了会出什么事

刚才只有一个选项。现在把三个都接上，还是因果：

s q  m o₁  m o₂  m o₃

问一句：o₁ 那个位置的隐藏状态里有什么？

有 s、q、o₁。没有 o₂ 和 o₃——它们排在 o₁ 后面。

而 o₃ 的隐藏状态里有 s、q、o₁、o₂、o₃，前面所有的东西。

麻烦就在这儿：同一道题的三个选项，是在三种不同的信息条件下被打分的。 排在后面的能看见前面的，排在前面的看不见后面的。

后果很具体：换个顺序，答案就可能变。

这个改不了。训练再多也不行——在训练集上，模型能学到「如果 billing 排在第一位，它更可能是答案」这种规律，而这条规律在真实世界里是假的，纯粹是排版造出来的。

这个现象叫选项翻转率。有人在同一套权重、同一批题上测过，只改选项顺序：

数据集选项数翻转率至少翻过一次的题
XNLI30.00130.33%
Emotion60.047711.0%
MASSIVE200.160029.7%

先看清这两个指标的分母，否则会读错一倍以上：

  • 翻转率的分母是重排副本——每道题生成若干种排列，每一种叫一个副本，统计其中有多少副本的答案和原排列不同。
  • 「至少翻过一次的题」的分母才是题。

以 MASSIVE 为例：300 道题做成 1500 个重排副本，其中 16.0% 的副本翻了；而有 29.7% 的题，至少有一种排列会翻。

所以准确的说法是：MASSIVE 上 16% 的重排副本换了答案，近三成的题受影响。

这里有个反直觉的地方：选项越多，翻转率越高，但原因不是「选项多所以乱」。

  • Emotion 只有 6 个选项，翻转率 0.048；
  • MASSIVE 有 20 个选项，翻转率 0.160；
  • XNLI 只有 3 个选项，翻转率 0.0013。

如果只看选项数，Emotion 的 6 个和 XNLI 的 3 个差不多，翻转率却差 37 倍。真正的差别在语义距离：XNLI 的三个类别是蕴含 / 中立 / 矛盾，彼此判然有别；Emotion 的六个情绪之间有大量重叠（joy 和 love、fear 和 surprise 常常同时成立），位置信息足以把结论推到相邻的类上。

同一个模型，一边是 0.13%，一边是 16%——差 120 倍。 这个指标必须按数据集看，取平均没有意义。

翻转率高的那个做法，行话叫 listwise：分数依赖整个候选集，换个队友分数就变。下面编码器的做法叫 pointwise：每个选项各算各的，跟别人无关。这两个词在后面还会反复出现。

5. 编码器怎么避开这一条

常规做法很干脆：一个选项跑一次前向。

前向 1:  [CLS] s q o₁  →  读 [CLS] → z₁
前向 2:  [CLS] s q o₂  →  读 [CLS] → z₂
前向 3:  [CLS] s q o₃  →  读 [CLS] → z₃

每次只放一个选项，o₂ 压根不在 o₁ 那次前向里，交换顺序当然不影响任何东西。这就是编码器天然的置换不变性。

代价很直接：三个选项三次前向。而且 state 那么长，每次都重新编码一遍。

选项数上去就很吓人。一个常见的上限是每问题 255 个选项，照这个做法就是 255 次完整前向，每次都把整段 state 过一遍。

6. 解码器能不能也切开

能。这就是 DUAN 的做法。

想法是把三个选项排在同一个序列里，但让它们互相看不见：

s q  │  o₁ m  │  o₂ m  │  o₃ m

注意力长这样：

           s q │ o₁ m₁ │ o₂ m₂ │ o₃ m₃
       s   ■ · │  · ·  │  · ·  │  · ·
       q   ■ ■ │  · ·  │  · ·  │  · ·
      o₁   ■ ■ │  ■ ■  │  · ·  │  · ·
      m₁   ■ ■ │  ■ ■  │  · ·  │  · ·
      o₂   ■ ■ │  · ·  │  ■ ■  │  · ·
      m₂   ■ ■ │  · ·  │  ■ ■  │  · ·
      o₃   ■ ■ │  · ·  │  · ·  │  ■ ■
      m₃   ■ ■ │  · ·  │  · ·  │  ■ ■

每一段看得见前缀 s q，也看得见自己，看不见别的段。中间那几块全空。

于是每一段的计算，和「把这一段单独接在前缀后面」一模一样。 数学上这就是三次独立的前向。

但它们被打包进了同一个张量。这不是把三次算变成一次，而是把三次算合并成一批：

项目分开跑三次合并成一批省了什么
选项段本身的矩阵乘3 份3 份没省
前缀 s q 的编码3 份1 份省 2 份
权重从显存读到计算单元3 次1 次省 2 次
内核启动、调度3 次1 次省 2 次

所以「一次前向」说的是批次数，「逐项打分」说的是分数依赖谁。两句话在不同层面上，不冲突。

如果只记一件事：计算量一点没少，省的全是重复的那部分——重复的前缀、重复的权重搬运、重复的调度开销。

上面那张矩阵回答的是另一个问题：段与段之间全空，所以 z₁ 不依赖 o₂、o₃，交换它俩只交换两个 logit。

还有一步不能漏：位置要跟着重算。

模型怎么知道谁排在谁后面？靠 RoPE——旋转位置编码，把「这是第几个 token」编码进注意力的分数里。这是 Qwen3 这类模型唯一的位置信号。

如果三段的 RoPE 位置还接着往下排（0,1,2,3…），模型仍然能算出「o₂ 排在 o₁ 后面」，那掩码就白改了。所以每段的位置都从前缀长度重新开始，三段用的是同一组位置。

掩码和位置一起改，才真的等价于「单独跑」。

那编码器为什么不能也这么办？ 能，原理上完全可以——给它加同一套分段掩码和位置重算，得到的计算图和一摸一样的因果模型没有区别。

排除它的理由有三个，都不是「做不到」：

  1. 要自己实现。 因果模型天生就是这样，掩码是免费的。编码器的双向掩码要手写，而且 RoPE 位置重算、KV 缓存也得跟着改。
  2. 权重没在这种可见范围下待过。 Laya 的 ModernBERT 是按 MLM 训的，训练时每个 token 都看得见全文。突然切成分段，它没见过这种条件。
  3. 拿不到那批预训练语料。 就算愿意重训，Qwen3 那批中文预训练数据是现成的，重新对齐一个中文 ModernBERT 不是。

所以这是成本问题，不是原理问题。design.md 第 4.1 节的 D 方案走的正是这条路，它的定性是**「原理上可行」**，只排除在成本上：

加段级掩码后三条性质都满足，问题是：mask 和位置重计要自己写，权重又是按 MLM 训的、没在这种可见范围下待过，微调成本不比 E 低，还拿不到 E 那批中文预训练语料。

注意 design.md 真正「被排除」的是 A 和 B 两条（A 结构性不可行，B 成本随选项线性增长），D 只是没被选。

7. 切开之后还剩三个问题

7.1 选项不能互相比了，还行吗

这是最让人不放心的一点。o₁ 看不见 o₂，模型怎么知道在这三个里挑哪个？

答案比想象的简单：选哪个只由分数大小决定，跟能不能互相比无关。

softmax 是单调的：

$$\arg\max_k \frac{e^{z_k}}{\sum_j e^{z_j}} = \arg\max_k z_k$$

三个分数都是同一把尺子量出来的——同一组权重、同一个读取位置、同样的前缀——所以它们本来就在一个尺度上，比大小就行。

那「互相看得见」到底多给了什么？

多给的是信息。模型知道「候选集里还有别的什么」，可以据此调整判断，比如学到「如果 legal 也在候选里，这单更可能是 billing」。这个信息切开之后就没了。

这是真的损失，不是能糊弄过去的。但它不是「没法选」，是「少了一点上下文」。

还有一个中间方案值得看一眼，因为它说明了「可比较性」到底靠什么实现。

这个方案叫拆分编码器：把 state 交给一个编码器算一次并缓存，然后让问题和选项走另一套带 cross-attention 的结构。选项之间怎么摆，它有自己的答案——互不可见，但看得见彼此的标记：

问题头 token  →  看问题头 + 所有选项的标记
选项 body    →  看问题头 + 自己这一段 + 所有选项的标记
选项标记     →  看问题头 + 自己这一段 + 所有标记

关键在第二行和第三行：选项 body 看不见别的选项的正文，但看得见每一个选项的标记。

打个比方：三个人分别在小房间里，看不见彼此的纸条，但能看见墙上挂着的三张标签。于是谁都能说「我这张纸条和墙上那三张标签是什么关系」，间接地把自己和同伴放在同一个坐标里。

这就是「介于 pointwise 和 listwise 之间」的确切含义：

像 pointwise 的地方像 listwise 的地方
选项 body 之间互不可见都看得见同一组标记
没有位置偏差（段位置都重算）分数隐含依赖「这一组里还有谁」

代价也随之而来。 那个「墙上的标签」是同一组，只在同一行里成立。选项超过 32 个要切块，每块是独立的一行、墙上挂的是不同的标签集合——于是跨块的分数没法直接比。所以这类方案必须靠随机分块训练，让模型学会在任意分块下都给出可比的分数。

DUAN 把这条路也切断了：连标记通道都不要，每段只看得见前缀和自己。换来的是任何分块下每段都独立算、跨块天然可比；付出的是候选集上下文。

（「标记通道」这个词，指的就是「选项能看到别的选项的标记」这条信息路径。拆分编码器留着它，DUAN 切掉它。）

分块到底会造成多大差异，可以看一个实测。 这个实测跑的是 Laya（一个现成的编码器决策模型），不是上面那个拆分编码器。这一点很重要：它的数字衡量的是 Laya 的分块行为，不能直接套到拆分方案上。

先说清实验设置。 300 道 banking77 题，每题 64 个选项（金标 + 63 个随机抽）。三种跑法：一次跑完，以及按 8 / 16 / 32 个一块分别跑（注意这是三种块大小，不是「切成三块」——64 个选项按 8 切是 8 块，按 32 切是 2 块）。

对照一致率
一次跑 vs 块 80.623
一次跑 vs 块 160.600
一次跑 vs 块 320.593
8 / 16 / 32 三种块大小互相之间0.790

这两栏都要小心读，没有一栏是「纯」的。

0.790 常被当作「分块尺度问题」的干净度量，其实也混了 token 预算。因为 Laya 的拥挤规则是 max(4, (head_max_len - 16) / k)，head_max_len 是 192，于是每个选项能分到的 token 数是：

所以 8 / 16 / 32 之间既差分块尺度，也差每选项的 token 数。报告本身也只说这是 logit 尺度的问题，没有声称这一组排除了预算因素。

0.593–0.623 那一栏混得更重——它把「一次跑（4 token）」和「分块（5.5 到 22 token）」对比，两个变量同时变了。

证据是分块之后准确率反而更高：banking77 的 Top-1 在一次跑时是 0.523，分块后升到 0.607–0.623。如果这个对照真在衡量「结构缺陷」，不该出现这种方向。

还有一个陷阱：这两组数字的区间几乎重叠，但不是一回事。

  • 「一次跑 vs 分块的答案一致率」= 0.593–0.623
  • 「分块后的 Top-1 准确率」= 0.607–0.623

前者衡量「两次跑答得一样不一样」，后者衡量「答得对不对」。看的时候盯指标名，不要盯数字。

那能从这个实验里得出什么？ 只有一条是稳的：分块会改变 Laya 的答案，而且改变幅度不小。 至于其中多少来自可见性、多少来自 token 预算，这个实验分不开——需要固定 token 预算重做一次才能定。

DUAN 不需要这个实验就能保证分块等价，因为它的段与段之间没有任何信息通道，任何分块下每段都独立算。这是设计的推论，不是实测结论；P4 会用「标记放在选项前面」的布局做对照，量出翻转率。

7.2 档位顺序丢了

前面一直用 choice 举例。score 题不一样，值得单独说，因为它的选项有顺序。

一份工单的紧急程度可以打 1 到 5 分。这五个档位本身有方向：1 分和 2 分是相邻的，1 分和 5 分是完全相反的两端。

位置重算把这层顺序抹掉了——五个档位段的位置都一样，模型看不出哪个是第一档、哪个是第五档。所以要另外把顺序喂给模型：

$$u_i = h_i + \mathrm{ord_emb}(i, k)$$

i 是第几档，k 是一共几档。这个向量是学出来的，输入四个数：[i/(k-1), (i/(k-1))², sin(πi/(k-1)), cos(πi/(k-1))]。

加在哪里还有待定。 design.md 目前先加在输出端（就是上面这个式子，$h_i$ 是标记的隐藏状态，加完再进打分器）。另一个选择是加在输入端的 ⟨lvl⟩ 嵌入上，让主干从第一层就能看到档位。两种都说得通，P4 做一次对照来定。

差别只在「模型第几层开始知道档位」：加在输入端，前 28 层都能用这个信息；加在输出端，只有最后的打分器知道。这不是「是否引入顺序」的差别——两种都引入了。

为什么补这个不算「又把位置偏差带回来了」？

因为抹掉的和补上的不是同一样东西。位置重算抹掉的是「谁排在序列前面」——那是渲染顺序造成的偶然事实。ord_emb 补的是「这是第几档」——那是数据本身的属性。调用方把档位倒过来传，ord_emb 跟着倒，答案也应该跟着倒。

判断标准就一条：打乱顺序，分数跟着它自己的选项走。ord_emb 满足，RoPE 位置不满足。

7.3 缓存到底存的什么

DUAN 能缓存，这是选它的主要理由之一。但这里有个容易混的地方。

「前缀」在两种语境下不是一回事：

  • 一次前向里的前缀：s 加 q。同一道题的所有选项段共用它。不同问题的 q 不同，前缀就不同。
  • 跨请求的缓存：只有 s。同一个 state 上来了新问题，s 已经算过的中间结果（KV，也就是注意力的 key 和 value）直接读出来，只有 q 和选项要重算。

所以「同一个 state 上十个问题共享前缀」，共享的是 s 那一截。q 每个问题都得算一遍。

Laya 做不到。它的 state 和问题从第 0 层就互相看得见，加一个问题，state 的表示就得全部重写。实测：同一个 state 上问题数从 1 加到 10，136ms → 993ms，7.3 倍，基本线性，说明一点没复用。

而选项数从 2 加到 32（16 倍），耗时只涨到 4.9 倍——因为选项变多只是序列变长，前向次数没变。这两个数字放一起看才完整：Laya 省了前向次数，赔了 state 复用。

8. 几种做法摆一起

这四种做法的根本区别是：一次前向装得下多少东西。 用这个视角看，表格不会歧义。

做法一次前向的单位state 编码几次选项之间换顺序会变吗
标准编码器一个（state, 问题, 选项）每选项 1 次不在同一序列不会
Laya一个（state, 问题）每问题 1 次互相看得见会
拆分编码器一个（state, 问题块），块 ≤ 32 选项1 次（可缓存）看不见，但共用标记块内不会，跨块不可比
DUAN整个请求（state + 全部问题 + 全部选项）1 次（可缓存）看不见，也不共用任何东西按构造不会

从第一行看到最后一行，就是「一次前向装的东西越来越多」：一个选项 → 一个问题 → 一个块 → 整个请求。

两个容易读错的格子：

  • Laya 不是「每个请求一次」。 它每个问题一条序列，一个请求里有 10 个问题就跑 10 次。实测问题数 1 → 10 耗时 7.3 倍，正是这个线性关系的证据。
  • 拆分编码器的 64 选项不是两块就完事。 选项超过 32 个时，先按块打分，再把概率最高的 16 个合起来重打一次。所以 64 选项 = 2 次分块前向 + 1 次联合重打。

DUAN 那一行的「按构造不会」是设计推论，还没有实测——P4 会用「标记放在选项前面」的布局做对照量出来。

9. 三个容易讲错的地方

「因果模型的表达能力更弱」。 不对。在给定序列上，它只是信息流受限，判别精度不必然更低。真正的代价在成本、对称性和可复用性。

「编码器一次前向就能给所有选项打分」。 对标准编码器来说不对，它是一次一个选项。把选项全塞进一个序列确实能一次跑完，Laya 就这么干，但代价是选项互相看得见。

「一次前向就是 listwise」。 不对。一次前向说的是算了几批，listwise 说的是分数依赖什么。DUAN 一次前向，但分数只依赖单个选项。判断看矩阵的形状：只看选项段和选项段之间那块区域有没有连线，不看前缀那块（它在哪种做法里都是下三角）。

一次请求的数据流

这是 U3 的参考答案。先合上这一页，自己把图画出一次，画完再回来对照。

我们跟着一个真实请求走一遍：从一段 JSON 进来到一个类型化答案出去，中间经过了什么。重点是DUAN 换掉了哪一段——这是画数据流图时最容易画错的地方。

先看请求长什么样

{
  "state": {"subject": "Refund", "body": "上个月我的信用卡被扣了两次款，请立即退款。"},
  "questions": [
    {"type": "choice", "instructions": "该转给哪个团队",
     "criteria": [{"label": "billing"}, {"label": "sales"}, {"label": "legal"}]}
  ]
}

一个 state 加一组问题。每个问题有类型、指令和候选。模型要输出的是每个问题的答案字段，不是文本。

Laya 怎么走完这一程

Laya 收到这个请求，把所有东西拼成一个序列：

[CLS] 问题 [SEP] [MASK] 选项0 [MASK] 选项1 [MASK] 选项2 [SEP] state [SEP]

注意三件事，它们后面都会变成问题：

  1. state 在最后。 所以 state 能看见前面的问题——但同时也挤在末尾，长 state 会被从尾部截断。
  2. 每个选项前面有一个 [MASK]。 这是读分数的位置。
  3. 选项之间互相看得见（第 3 条其实和上一条是一件事的两面：[MASK] 能看到整段）。

然后：

flowchart LR
    req["JSON 请求"] --> render["渲染: 问题, 选项前的 MASK, 末尾的 state"]
    subgraph laya ["Laya: 被替换的一段"]
        enc["编码器"] --> head2["2 层 head"]
    end
    render --> enc
    head2 --> gather["gather: 读 MASK 位置"]
    gather --> scorer["scorer"]
    scorer --> calib["校准"]
    calib --> answer["类型化答案"]

编码器跑完，gather 从三个 [MASK] 位置各取一个隐藏状态，送进 scorer，每个得到一个 logit，softmax 之后就是概率。

DUAN 换掉了哪一段

不是整个 Laya。 换掉的只是中间那两块：编码器 + 2 层 head。

框外面三件东西都留着：请求解析、scorer（决策头）、校准、答案组装。这是必须说清的一件事，因为它决定了 DUAN 要重写多少代码。

flowchart LR
    req["JSON 请求: state + questions"] --> render["渲染: state, 问题, 互不可见的选项段"]
    subgraph duan ["DUAN: 换成这一段"]
        qwen["Qwen3-0.6B 因果解码器"]
    end
    cache["state 前缀 KV 缓存"] -.-> qwen
    render --> qwen
    qwen --> head["决策头: 每段结尾标记的隐藏状态到 logit"]
    head --> calib["校准: softmax(z / T)"]
    calib --> answer["类型化答案: choice / score / noul"]

两处关键差别：

读分数的位置变了。 Laya 读选项前面的 [MASK]，DUAN 读选项后面的结尾标记。原因见 encoder-decoder.md 第 3 节——因果模型里，位置只能看见自己之前的内容，放在选项前面的标记根本不知道选项是什么。

gather 消失了。 Laya 需要它是因为三个选项在同一个序列里，得按位置把三个 [MASK] 的隐藏状态挑出来。DUAN 也有这一步，但它不是独立节点——决策头读的就是各段末尾那个位置，不需要另外挑。

跟着一个值走

把 billing 这个选项追到底：

步骤发生了什么输出的形状
解析{"label":"billing"} 变成结构体一个 Criteria 对象
渲染变成 billing 三个 token，后面接 ⟨opt⟩token id 序列

每个节点要注意什么

JSON 请求。 POST /v1/systemone。解析时做一轮校验：最多 256 个问题、255 个选项、32 个等级。代价矩阵、排列平均、短名单这类可选扩展也在这里解析。

渲染。 这是两个项目差别最大的地方。DUAN 的顺序是 [state] [问题 1] [选项 1.1] ... [问题 2] [选项 2.1] ...，每段是「选项文本 + 结尾标记」，位置从 n + len(问题块) 重新开始。

Laya 的渲染长这样：

[CLS] tok("<type> question: <instructions>")[:budget] [SEP]
[MASK] tok(" " + opt_0)[:48] ... [SEP]
tok(state)[:room] [SEP]

选项上限 48 token，如果总长超过 head_max_len 就每个压到 max(4, ...)。state 从尾部截断，而且是静默的——这是个已知缺陷（Laya #174）。

两边都要防一件事：用户文本里如果字面写着 [MASK] 或 <mask>，渲染时替换成空格，否则用户可以伪造标记。DUAN 的标记用的是词表外的 id，分词器压根产生不了，所以理论上不需要这层防护，但保留着没坏处。

Qwen3。 一次带分段掩码的前向，读完所有问题和选项。零样本时也可以不用决策头，直接读标签 token 的概率当分数——实测这道题 0.6B 选了 sales（0.488）而不是正确的 billing（0.447）。这是 P4 要超越的起点。这个读法有四个坑，见下方「零样本的四个坑」。

state 前缀 KV 缓存。 同一个 state 上的多个问题可以共用。Laya 做不到：问题数从 1 加到 10，136ms → 993ms，7.3 倍，基本线性，说明 state 每问都重算。DUAN 靠 Qwen3 的因果结构白得。

有个细节容易搞错：Laya compat 的响应里没有 cache 字段。文档里那个 "cache": {"state": "hit", "answers": "miss"} 示例属于扩展块，只在原生模型的响应里出现。所以 P8 没有 Laya 侧的现成参照可比，得自己测。

决策头。 Laya 是 LayerNorm(d) → Linear(d,d) → GELU → Linear(d,1)，每个选项出一个 logit。DUAN 用同样形态，但多一个按题型的偏置，作用在每个选项段结尾标记的隐藏状态上。

score 题还要额外加序数嵌入，因为位置重计之后模型看不出档位顺序（encoder-decoder.md 第 7.2 节）。

校准。 温度按 (type, k_bucket, lang_group) 三键查找：先找完全匹配，逐级回退到更粗的桶。k 桶是 2 / 3-5 / 6-10 / 11-31 / 32-255，温度裁剪到 [0.25, 8.0]。

这里修掉了 Laya 的一个不一致：它拟合时用 [0.1, 10]，运行时用 [0.5, 5]。拟合和运行必须是同一个范围，否则拟合出来的温度在运行时会被再次裁剪掉。

顺带一个观察：laya-multilingual 这个快照的 checkpoint 里 temperature = [1.0, 1.0, 1.0]、temperature_by_options = {}——它根本没带拟合过的温度。

类型化答案。 choice 给 choice + probabilities + confidence；score 给 score = Σ i·p_i、legend、probabilities；noul 给 noul = p[1]。三者都带 action.act_probability。

confidence 有两个公式，很容易混。实测同一个 urgency 问题：

  • confidence = 0.1243，用的是熵公式 1 - H(p)/ln k
  • answer_confidence = 0.3686，用的是 max(p)

报告里两者都被叫作「置信度」。取数之前先确认拿的是哪个。

零样本的四个坑

tools/ref/qwen_zero_probe.py 读标签 token 的概率当分数，机制成立但很脆：

  1. 标签不能出现在 prompt 里。 否则模型是在复制标签，不是在选。
  2. 候选标签的首 token 必须互不相同。 option 1..4 的首 token 都是 option，归一化之后必然是四个 0.25。这不是「模型觉得四个一样」，是读法失效。
  3. 对空格和大小写敏感。 billing（1.6e-8）和 billing（6.1e-7）差 38 倍。
  4. 作答前缀要和模型实际的输出格式一致。 否则单 token 的标签（比如 other）会占便宜。

所以 DUAN 用学出来的标记加打分器，不用这套读法。

DUAN 模型规格

这份文档回答一个问题：DUAN 要做成的模型具体长什么样。plan.md 的每个里程碑都是为了把这里的某一节做出来，learn/ 的每个学习单元都是为了能看懂、做出某一节。

规格里写「待定」的地方，都注明由哪个阶段的哪个实验来定。实验定下来以后改这份文档，不另写。

1. 目标与非目标

目标： 一个中文为主的 System One 决策模型。输入一段 state 和若干问题（choice、score、noul），一次前向输出每个问题的校准概率。

终点的验收标准，也就是 P4 的完成标准：

  • 在中文评测集上，NLL 和 ECE 优于用同一批数据、同样损失微调的 laya-multilingual；
  • 至少 3 个随机种子；
  • 选项翻转率接近 0，剩下的只是浮点误差。

非目标：

  • 不生成文本，不做对话。
  • 不复刻 Jev 的内部结构。
  • 不追求亚毫秒延迟。那条路要走蒸馏，见 P8。
  • 不做 HTTP 服务。DUAN 提供模型和推理库，需要服务时接一层，而不是把它做进模型。

2. 固定下来的约定

3. 输入布局

3.1 序列由三类块组成

一个 state 和它上面的所有问题，排成一个序列，做一次前向：

[state 块] [问题块 1] [选项段 1.1] [选项段 1.2] ... [问题块 2] [选项段 2.1] ...
  • state 块： state 的 token。字符串直接分词；JSON 先压成紧凑格式（, 和 : 后不留空格，键顺序保持请求里的顺序），再分词。
  • 问题块： 题型标记 ⟨choice⟩、⟨score⟩ 或 ⟨noul⟩，后面接 instructions 的 token。
  • 选项段： 一个选项的文本，后面接这一题型的结尾标记。决策头读取的是结尾标记的隐藏状态。

3.2 可见范围

可见范围由注意力偏置 bias 决定：看得见的地方填 0，看不见的地方填一个很大的负数。规则如下：

查询所在的块能看见
state 块state 块中自己之前的 token（因果）
问题块 j整个 state 块，以及问题块 j 中自己之前的 token
选项段 (j, i)整个 state 块、整个问题块 j，以及选项段 (j, i) 中自己之前的 token

问题块之间互不可见，选项段之间也互不可见。所以，同一个请求里多问一个问题，不会改变其他问题的答案。通常这个性质要靠「在同一请求里塞干扰问题」的数据增强来训练，而在这里它由结构保证，不需要训练。

3.3 位置

RoPE 位置也要随块重计：

  • state 块：位置从 0 到 n-1。
  • 每个问题块：都从 n 开始。
  • 问题块 j 的每个选项段：都从 n + len(问题块 j) 开始。

只改掩码是不够的。如果位置不重计，选项段的位置仍有先后，模型照样分得出谁排在前面。掩码和位置都改了，每个选项段的计算才和「把它单独接在前缀后面」完全一样。

3.4 由布局直接推出的三条性质

这三条都是分段布局 + 位置重计的直接推论，不靠训练学会。第 4.1 节的表里也会出现这几条，但那张表比较的是五条路线各自的代价（多几次前向、要不要额外结构），不是另一套性质。

  1. 交换两个选项，只会交换它们的 logit。 选项翻转率按构造为 0，测出来不为 0 的部分只是浮点误差。

  2. 选项可以分批前向，结果不变。 每个选项段只依赖前缀和它自己，所以超长的选项列表可以拆成几批来算，logits 相同。第 4.1 节的 C 方案（拆分编码器）做不到这一点：那类方案的选项段彼此看不见，但共用同一行里的所有标记，所以跨块的标记集合不同、logit 尺度也不同，跨块不可比，必须靠「随机分块」增强。DUAN 的选项段之间连共享标记都没有，任何分块下每段的计算都与单独前向一致，不需要这项增强。

    注意「结果不变」的严格程度：批形状改变会改变矩阵乘的归约顺序，所以只保证数值等价到浮点误差，不保证 bit-exact。

  3. state 只算一次。 state 块的 KV 只依赖 state 本身，可以缓存下来，供同一 state 上后来的问题复用（第 7 节）。

这三条合起来就是「一次前向、逐项打分」：一次前向是把各段拼在一个张量里（工程），逐项打分是各段互不可见、位置重计（数学）。两者不矛盾，前者省的是重复的权重加载和前缀计算，不是把 $k$ 次计算变成 1 次。推导见 learn/encoder-decoder.md 第 6 节的块对角矩阵。

代价是选项之间不能直接比较，候选集只通过 softmax 归一化起作用。这不影响 argmax：softmax 单调，$\arg\max_k z_k$ 与归一化无关。丢掉的是「看到候选集据此调整打分策略」这份信息，不是「选出最好的那个」这个能力。如果某类问题确实需要联合比较，只对排名靠前的几个选项做一次联合打分，不退回顺序拼接。这一点要等到出现具体需求时再设计。推导见 learn/encoder-decoder.md 第 7.1 节。

3.5 三种题型怎么渲染

题型选项段结尾标记
choicelabel: description，没有 description 时只写 label⟨opt⟩
score第 i 档的 criteria 文本，不写档位序号⟨lvl⟩
noul两段：「不成立」一段和「成立」一段，各自的 criteria 文本可以为空分别是 ⟨no⟩ 和 ⟨yes⟩

需要说明的几点：

  • score 的选项段不写序号，各段的位置又都相同，模型看不出档位顺序。顺序信息由第 5 节的序数嵌入提供。调用方把档位倒过来传，得到的应该是倒过来的分布，而不是另一个判断。
  • noul 不插入 "true"、"false" 这样的词，极性只由 ⟨no⟩ 和 ⟨yes⟩ 两个标记区分。这样可以修掉 Laya 跟着标签字面走的缺陷（Laya issue #156）。
  • 用户文本中如果出现标记的字面写法，渲染时替换成空格，防止伪造标记。

3.6 标记 token

一共有 7 个标记：⟨choice⟩、⟨score⟩、⟨noul⟩、⟨opt⟩、⟨lvl⟩、⟨no⟩、⟨yes⟩。截断时用的 ⟨cut⟩ 另算。

Qwen3-0.6B 的嵌入矩阵有 151,936 行，而分词器只用到大约 151,669 个 id，后面空着的行可以拿来放新标记，不需要扩词表。

  • 这些 id 分词器不会产生，所以用户文本无法拼出一个标记。
  • 新标记的嵌入初始化为普通 token 嵌入的均值，再加 std 0.02 的噪声，然后在训练中学习。

待定（P3）： 用分词器确认实际用到的 id 数和空行范围，然后在这里写死每个标记的 id。

4. 主干

4.1 为什么是因果解码器

第 3 节那套布局，说到底只要求一件事：state 段的表示不能依赖问题或选项，选项段之间不能互相看见。

为什么？因为只有这样，state 才能算一次就被复用，选项才能各自独立打分。这两条是 P4 和 P8 的基础。

注意这个要求是段级的，不是 token 级的。 有两种办法能做到：

  • 靠因果注意力（E 方案）：state 的 token 本来就看不在它后面的东西，问题块排在它后面，天然看不到。
  • 靠分段掩码（D 方案）：双向注意力加 mask，让 state 段只在自己内部互相可见。段内仍是双向的，但加一个选项不会改写 state 段，缓存照样成立。

所以 D 在原理上完全可行。它的代价不在原理，在工程——要自己写 mask 和位置重计，而且权重是按 MLM 训出来的，没在这种可见范围下待过。

真正做不到的是不加任何掩码的双向注意力：只要某个 token 能看见它后面的 token，加一个选项就会改写前面选项的表示。这就是 Laya compat（A 方案）的处境。

在这个约束下，五条路线各自的代价。表里 C 那一行需要先说一句：

C 是「拆分编码器」。 它把 state 交给一个编码器算一次并缓存起来，然后让问题和选项走另一套带 cross-attention 的结构去读这份缓存。state 只算一次的目标达到了，但它和上面那条「选项段之间不能互相看见」的要求差一点——为此它加了一个折中（选项之间看不见正文，但能看见彼此的标记），代价在后文说。这是唯一一条已经在真实系统里跑到大规模的实现，所以值得单独列出来对照。

方案每个问题的前向打分state 编码次数选项位置偏差state 能否复用需要的额外结构
A. 沿用 Laya compat（ModernBERT，全序列一次前向）1listwise每问题 1 次有，实测翻转率 0.0013–0.160否无，但三条性质一条都不成立
B. 标准编码器逐项打分k（每选项 1 次）pointwisek 次无否无
C. 拆分编码器1（每 32 个选项一块）介于两者之间：段间互不可见，但共用标记可互比1 次无是，状态缓存state 塔、问题塔、cross-attention、蒸馏
D. 编码器加自定义分段掩码1pointwise1 次无是手写段级掩码与位置重计；权重没在这种可见范围下训过
E. Qwen3-0.6B-Base 因果解码器（采用）1pointwise1 次按构造为 0是，由结构白送只需 forward_with(ids, positions, bias, caches)

表里「前向」和「打分」是两列，不要连起来读：B 慢是因为每个选项单独前向；A 快是因为把选项塞进了同一个序列，代价是选项互相看得见。E 两者兼得——它用分段掩码把「塞进同一序列」和「互不可见」同时做到了。但注意计算量没省，省的是重复的权重加载和前缀计算。

逐条说为什么这样选：

  • A 不行，它的代价是结构性的。 state 和问题从第 0 层就互相可见，什么都缓存不下来。实测同一 state 上问题数 1 → 10，耗时 7.3 倍（P0 实测记录）——而 P8 的验收标准就是用这个场景，说明它不是边界情况。
  • B 不行，成本随选项数线性增长。 每个选项一次完整前向，长 state 被重复编码 k 次，而 k 最大到 255（第 3.7 节）。
  • C 可行，但要付两次钱。 它靠多一套结构和教师蒸馏把「state 只算一次」换回来，代价是 state 的表示不能随问题调整。这个精度损失要等实测才知道。它愿意付，是因为要在同一套 ModernBERT 权重上和 Laya 对拍；DUAN 没有这个包袱。
  • D 原理上可行，但它是在编码器里手工重建因果结构。 加段级掩码后三条性质都满足，问题是：mask 和位置重计要自己写，权重又是按 MLM 训的、没在这种可见范围下待过，微调成本不比 E 低，还拿不到 E 那批中文预训练语料。
  • E 是唯一「布局直接落地、不需要额外结构」的一条。 第 3.4 节那三条性质都是它的推论，而不是需要训练才能学会的行为。

这条选择的两个前提，要分清哪个已经确定、哪个还要检验：

  • 结构收益是确定的。 前向次数、state 复用、置换不变性都可以从第 3 节直接推出来，与权重无关。
  • 能力收益还是假设。 「Qwen3 在中文上更强」目前没有同数据对照支持，P4 就是用来检验它的（plan.md 的「风险」）。输了照实报告差距，并重新评估这个选择。

代价有三条，都写进了验收或后续阶段，不是遗留问题：

  • 选项之间不能直接比较。 候选集只通过 softmax 归一化起作用（第 3.4 节）。出现确实需要联合比较的题型时，只对排名靠前的几个选项加一次联合打分，不退回顺序拼接。
  • 解码器不是判别模型。 它是 CLM 预训练，某个位置的隐藏状态本质上是「下一个 token 会是什么」的中间量，所以要读选项文本之后的位置（第 3.5 节的结尾标记），并且必须微调，不能指望零样本。零样本读法机制成立但很脆，只作参考：tools/ref/qwen_zero_probe.py，实测与四个陷阱见 P0 实测记录。
  • 规模是被算出来的，不是拍的。 0.6B 对应 plan.md 的延迟上限（GPU 个位数毫秒）和 24 GB 硬件能全量微调。后一条是估算：FP32 权重、梯度、AdamW 状态合计约 10 GB，这只覆盖参数相关的部分，不含激活值和注意力矩阵；实际可用 batch size 要等 P4 用真实的 state/选项长度测出来，见第 8 节的待定项。

推导过程的教学版本见 learn/encoder-decoder.md：从一个客服工单的例子讲起，可见矩阵、块对角矩阵为什么能同时是「一次前向」和「逐项打分」，以及四种布局的对照。

4.2 结构与参数

主干是 Qwen/Qwen3-0.6B-Base，在 crates/duan-qwen 中用 Burn 从零实现：

  • 28 层，隐藏维度 1024；
  • GQA：16 个查询头、8 个 KV 头，head_dim 128；
  • 在每个头上做 QK-norm；
  • RoPE，θ = 1,000,000，rotate-half 约定；
  • RMSNorm，eps 1e-6；
  • SwiGLU 前馈，中间维度 3072；
  • 所有线性层都没有偏置，输入输出共享嵌入。

接口：

  • Qwen::forward(ids, mask, caches) 处理普通的因果文本，用来和 transformers 对齐。
  • Qwen::forward_with(ids, positions, bias, caches) 由调用方给出位置和偏置，第 3 节的布局就靠它实现。

权重由 duan_qwen::load 从 HF 的 safetensors 加载：

  • BF16 转成 FP32；
  • 线性层权重从 [out, in] 转置成 [in, out]；

5. 决策头

对问题 j 的第 i 个选项段，取结尾标记位置的最终隐藏状态 h_i（维度 d = 1024），然后：

m_i = h_i + ord_emb(i, k)            只对 score 加
z_i = W_b · GELU(W_a · LN(m_i)) + b_type
p   = softmax(z / T)                 只在同一个问题的 k 个选项之间归一化

各部分的形状和初始化：

  • W_a 是 [d, d]，W_b 是 [1, d]，b_type 是 [3]，每种题型一个偏置。
  • ord_emb(i, k) 是一个线性映射，输入是 4 个特征 [i/(k-1), (i/(k-1))^2, sin(π·i/(k-1)), cos(π·i/(k-1))]，输出维度是 d。拆分编码器用的是同一套。
  • 新权重都按 std 0.02 初始化，W_b 和 b_type 初始化为 0。这样训练开始时所有选项的 logit 相等，概率是均匀分布。

从 p 得到答案字段：

  • choice： choice = argmax p。confidence 默认用 Jev 公式 clip((max p − 1/k) / (1 − 1/k))，也可以选熵公式 1 − H(p)/ln k。
  • score： score = Σ i·p_i，confidence 用 Jev 的平均绝对偏差形式。
  • noul： noul = p[1]，默认不输出 confidence。

三者都带 action.act_probability。Laya 的 act head 从没训练过，这个值不能当置信度；DUAN 在 P6 训练一个置信度头，AUROC 不高于 max(p) 就不发布它（P6 完成标准）。

待定（P4）： 序数嵌入加在输出端（上式），还是加在 ⟨lvl⟩ 的输入嵌入上，让主干从第一层就能看到顺序。先加在输出端，P4 做一次对照。

6. 训练与校准

损失，每个问题一项：

L = ProperScoreLoss(p, t) + w_ord · RPS(p, t)    RPS 只用于 score，w_ord = 1.0
ProperScoreLoss(p, t) = -( Σ t_i · log max(p_i, 1e-4) + 0.5 · (Σ t_i · p_i) / ||p||_2 )

DUAN 没有教师模型，也没有拆成两个塔，所以知识蒸馏项、隐藏状态蒸馏项和短名单项都不用。P4 对比 proper、ce、pg 三种损失，结论写回这一节。

增强： 只做和结构有关的几项：

  • 打乱 choice 选项的顺序；
  • 把 score 的档位镜像（50%）；
  • 随机改写 noul 的 criteria 措辞（30%）；
  • 把选项标签换成中性 id（20%）；
  • 随机截断（10%）。

「随机分块」和「同一请求中的干扰问题」两项不需要做，原因见第 3.2 节和第 3.4 节。

优化：

  • AdamW，β = (0.9, 0.98)，weight decay 0.01；
  • 学习率：新权重 1e-4，主干 3e-5，2% warmup，余弦衰减；
  • 梯度裁剪 1.0。

待定（P4）： 只训练顶部 N 层，还是全量训练。在 24 GB 级别的硬件上两种都跑一遍，比较指标和显存。

校准：

  • P1 先在留出集上拟合一个温度 T。
  • P6 改成按（题型、k 桶、语言组）分桶拟合，写出 calibration.json。
  • 拟合时和推理时用同一个裁剪范围 [0.25, 8.0]。
  • 校准只在人工标注的数据上报告。

7. 推理与缓存

先把「前缀」的两个层级分清，否则会误以为同一 state 上的所有问题能共享整段前缀：

层级包含复用范围
一次前向内的前缀state 块 + 所属问题块同一问题上，它的所有选项段共享
跨请求的缓存只有 state 块同一 state 上的后续请求直接读 KV
  • state 块做一次前向后，KV 缓存下来。同一 state 上后来的问题，只需要计算各自的问题块和选项段，forward_with 的 caches 参数负责这件事。问题块本身不跨请求缓存：它随问题内容变化，每个请求重算。
  • KvCache::len() 是新 token 在 bias 中的列偏移，而不是新 token 的 RoPE 位置。两者在选项段里不同：每段的 RoPE 位置都从 n + len(问题块) 重新开始。
  • 正确性以 flex 后端上的 FP32 为准，metal 和 cuda 后端先和它对齐。
  • 量化（bf16、int8）放到 P8，以 argmax 翻转率作为验收指标。

怎么测的

四件事，每件都单独跑：

  1. 起一个推理服务，加载 Laya 的 multilingual 权重，CPU 推理。
  2. 发三个请求，分别是一道 choice（team）、一道 score（urgency）、一道 noul（churn）。然后对同一道 choice 做四组改动：反转选项顺序、加一个错误选项、换成中性标签、原样。另外两题不动，作为对照。
  3. 扫两类规模：固定选项数改问题数（1 到 10），固定问题数改选项数（2 到 32），各跑三次取中位数。

两件事同时成立：

  • 反转选项顺序后，team 变了，另外两题一点没变。 说明每个问题单独前向，问题之间独立；变化只发生在同一个问题的内部。
  • 加一个明显错误的选项，team 几乎不动。 因为 billing 已经饱和在 1.0，softmax 没有余量可分。要观察候选集效应，必须先构造一个不饱和的问题。

缺陷二：答案依赖标签字面

描述完全不变，只把标签换成中性 id（option 1..4），team 就从 1.0 塌到 0.793。

这是「模型在读标签的字面，而不是在读描述」的直接证据。对应的补救手段是训练时随机把标签换成中性 id，让它学不到「标签叫什么」和「是不是答案」之间的虚假关联。

缺陷三：act_probability 不可用

三道题的 act_probability 全是 1.0，包括最大概率只有 0.3686 的 urgency：

team    | choice | confidence 0.9999 | act_probability 1.0
urgency | score  | confidence 0.1243 | act_probability 1.0
churn   | noul   | confidence 0.9883 | act_probability 1.0

原因很直接：这个头从没训练过（源码里乘了 0.0），实测 AUROC 0.30。所以 Laya 只能在 NLL、ECE、Brier 上当基线，act_probability 一列不能用。

一个必须说清的细节： 同一个 urgency，响应里的 confidence 是 0.1243，answer_confidence 是 0.3686。前者用的是熵公式 1 − H(p)/ln k，后者是 max(p)。报告里两者都被叫作「置信度」，取数前先确认拿的是哪一个。

Qwen3 零样本

指令版 Qwen/Qwen3-0.6B，使用聊天模板，只在候选集内归一化：

标签概率
sales0.4882（argmax）
billing0.4471

正确答案是 billing（客户被重复扣费并威胁取消）。0.6B 零样本选错了，而 Laya 给 billing 1.0。这就是 P4 要超越的起点。

读标签 token 的零样本读法本身成立，但有四个陷阱：

  1. 标签放进 prompt，模型会去抄标签。 prompt 里只能给描述，标签作为候选出现在作答的位置。
  2. 候选的首 token 必须互不相同。 option 1..4 的分词首 token 都是 option，归一化后必然全是 0.25。这不是「模型认为四个一样」，而是读法失效，要改成累加多个 token 的序列打分。
  3. 对空格和大小写敏感。 billing、 billing、Billing、 Billing 是四个不同的 token。实测 billing 1.6e-8、 billing 6.1e-7，差 38 倍——足以改变 argmax。
  4. 作答前缀要和模型实际的输出格式一致。 选项写成 - 标签: 描述 的列表时，模型常常先照抄 - 。直接在作答位置读标签，几个标签的概率都很低，单 token 的标签（如 other）少乘几个概率，就占了便宜。见反事实对照：不加前缀时 7 个请求里有 2 个和贪心生成不一致，都误选了 other。本节的数字是首 token 读法、不加前缀得到的，也可能受这一条影响。

这四个陷阱说明，读标签 token 的做法泛化不到任意标签集。DUAN 用学出来的结尾标记加决策头，原因就在这里（design.md 第 3、5 节）。

分析

  • Laya 没有读出国籍。 German 和 Italian 都选 Roma，而且写 German 时 Roma 的概率（0.9176）比写 Italian 时（0.6692）还高。Bayern 在三种 state 下都在 0.03 左右。同一句 German，把 Bayern 换成 Dortmund，Dortmund 以 0.4586 对 0.4072 险胜；only-german-team 一组把选项倒序，答案在 Roma 和 Dortmund 之间翻转。这是 P0 已记录的「选项排列会改变答案」和「答案依赖标签字面」在一道新题上的实例。
  • Qwen3-0.6B 按材料作答。 反事实对照下它跟着材料从 Bayern 换到 Roma，说明不是在背「谁拿过欧冠」。倒序前后都选 Dortmund（1.0 和 0.9889）。材料为空时选 other，在这个规模上，它的世界知识不足以单独答对这道题。
  • 换到路由题，Qwen3 零样本反而错了。 扣费邮件上它选 other，billing 只差 0.02；Laya 在这类题上训练过，给 billing 1.0。P0 用另一个 prompt 测过这封邮件，Qwen3 选的是 sales。两个 prompt 下都选错，但错的方向不同，说明 0.6B 零样本对 prompt 措辞很敏感。
  • 第四个零样本陷阱。 P0 实测记录列了三个陷阱。这里多一个：选项写成 - 标签: 描述 的列表时，模型常常先照抄 - 。在作答位置直接读标签，几个标签的概率都很低，只有一个 token 的 other 少乘几个概率，就占了便宜。用贪心生成核对读法，是发现这类问题最直接的办法。
  • 两者不能直接比较。 Laya 是一次前向给每个选项打分；Qwen3 用聊天模板和列表 prompt，对每个候选整段打分。只有两道题、七个请求，也没有多个种子，所以这里只说明现象，不能当准确率或校准的结论。
  • 对 DUAN 的意义。 「德国俱乐部 → 拜仁」这一跳，解码器骨干在零样本时就能完成。DUAN 用结尾标记加决策头替换读标签 token 的读法（design.md 第 3、5 节），P4 微调后这种能力是否还在，可以拿这组请求做回归检查。

尚未验证：

  • 换成 Qwen3-0.6B-Base、更大的 Qwen3，或者把选项写成中文，结论是否不变；
  • 更多需要一跳推理的题目上，Laya 和 Qwen3 的差距有多大。

bidirectional attention双向注意力每个位置能看到整段序列，任何 token 的加入都会改写前面的表示
pointwise scoring逐项打分每个选项的分数只依赖它自己，对选项排列不变。标准编码器实现要 $k$ 次前向；解码器用分段布局可以一次前向。注意「逐项」说的是分数依赖什么，不是前向次数。它不影响 argmax：softmax 单调，$\arg\max_k z_k$ 与归一化无关；丢掉的是候选集上下文，不是选择能力
listwise scoring列表打分分数依赖选项排列与候选集组成，因为选项在同一序列里互相可见
layout排法同一次前向里选项怎么摆。两个常见取值：顺序拼接（互相可见）、分段布局（互不可见且位置重计）。但排法不止两种：拆分编码器互不可见却共用标记，标准编码器则根本不把选项放进同一序列
forward count前向次数算了几次模型。它是排法的工程后果，不是结构的性质，也不决定打分方式
segment mask分段掩码让几段文本共用一个前缀、彼此不可见的注意力掩码；本项目用它把各个选项段放进同一次前向
position restart位置重计每个选项段的 RoPE 位置都从前缀长度开始，模型分不出选项的先后
marker标记决策头读取其隐藏状态的特殊 token。DUAN 的结尾标记用嵌入矩阵里空着的 id，分词器产生不了；Laya 的 [MASK] 是词表内的普通特殊 token，所以渲染时要把用户文本里字面的 [MASK] 替换掉
ordinal embedding序数嵌入加在 score 各档标记上的向量，告诉模型档位顺序，因为位置重计后模型看不出顺序。它跟着选项一起移动，所以不破坏置换不变性：位置重计消除的是「排版顺序」这个噪声，它注入的是「第 i 档 / 共 k 档」这个语义
RPS, ranked probability score有序概率评分按累积分布比较的评分规则，档位猜偏一档比猜偏三档惩罚轻；用于 score 题
GQA, grouped query attention分组查询注意力多个查询头共享一组键值头
RoPE旋转位置编码用旋转矩阵把位置信息乘进 Q 和 K，使注意力分数只取决于相对位置；Qwen3 用 rotate-half 约定，θ = 1e6
RMSNorm均方根归一化只按均方根缩放、不减均值，也没有偏置；Qwen3 的 eps 是 1e-6
QK-norm查询键归一化在计算 $QK^\top$ 之前对每个头的 Q 和 K 各做一次归一化；Qwen3 有，Llama 没有
SwiGLUSwiGLU 门控前馈门控前馈的一种，门用 SiLU；Qwen3 中间维度 3072，Llama 常用 4d
KV cache键值缓存保存已算过的 K 和 V，增量前向时只算新 token；KvCache::len() 是新 token 在 bias 里的列偏移，不是它的 RoPE 位置
prefix caching前缀缓存KV 缓存的一种用法：同一个前缀（例如 state）只算一次，多个后缀共用；P8 的收益来源
order flip rate选项翻转率调换选项顺序后答案改变的比例
permutation invariance置换不变性打乱输入顺序后输出不变的性质；pointwise 打分满足，listwise 不满足
chunk consistency分块一致性同一道题在不同分块方式下给出的答案一致率。有两种口径，不能混：①「一次前向 vs 各分块」，②「各分块之间」。在一份对 Laya 的实测里：①0.593–0.623（混有 token 预算差异），②0.790
contamination测试集泄漏训练数据里出现了和评测集近似的文本；用 MinHash + Jaccard 0.5 检查
distillation蒸馏让小模型学大模型的输出分布；DUAN 不用（design.md 第 6 节）
